# 펫 스프라이트 제작

## 먹이/간식 소품 — Eat 애니메이션과는 별개로 제작한다 (2026-08-07 추가)

`feed`(밥)와 `snack`(간식)은 같은 Eat 몸동작 애니메이션을 공유한다 — 몸동작으로 구분하지 않는다. 대신 캐릭터 옆에 잠깐 나타났다 먹으면서 점점 작아지는 **정지 이미지 소품 2장**(밥그릇/사료 1장, 간식 1장)으로 구분한다. 코드(`pet.gd`의 `show_food_prop()`)가 이 정지 이미지를 스케일·투명도 트윈으로 줄어들게 처리하므로, **프레임별 애니메이션 시트가 아니라 상태 하나당 정지 PNG 1장만** 만들면 된다.

- 파일명 관례: `assets/sprites/<character_id>/food_feed.png`, `food_snack.png` (진화 티어 구분 불필요 — 음식은 캐릭터 외형과 무관하므로 티어당 하나씩 만들 필요 없다. 티어 공용 1쌍으로 충분).
- 캐릭터의 케어 효과(`scripts/data/balance.gd`의 `CARE_EFFECTS`)와 어울리는 음식으로 디자인한다 — 예: 일반 사료/밥 vs 캐릭터 취향에 맞는 간식(과자, 과일 등).
- 배경 투명, 크로마키 없이 알파로 바로 제작 가능(작은 소품이라 sprite-gen의 component-row 파이프라인을 안 써도 되고, 단일 이미지 생성으로 충분하다).
- 이 소품은 선택 사항이다 — 없으면 `Characters.get_food_prop()`이 빈 문자열을 반환해 기존처럼 소품 없이 Eat만 재생된다. 신규 캐릭터든 레거시 업그레이드든, 다른 13상태와 별개로 언제든 추가/보완 가능하다.

## 이 스킬이 하는 일

`sprite-gen` 스킬(이미지 생성·크로마키 정리·프레임 추출 엔진, 로컬 설치: `~/.claude/skills/sprite-gen`)을 이 프로젝트의 시각 규칙에 맞춰 운전하는 절차를 담는다. sprite-gen 자체는 범용 스프라이트 도구이고, 이 스킬은 "aegis_pet에서는 어떻게 써야 하는가"를 담는다.

## 필독 원문 문서

**작업 시작 전 반드시 `docs/02-design/pet-sprite-production-guide.md` 전체를 읽는다.** 이 문서가 이 프로젝트 스프라이트 제작의 원본 규칙이며, 여기서는 sprite-gen 실행 절차와의 연결점만 요약한다. 특히 다음 섹션은 매 작업마다 다시 확인한다:
- §2 "시각적 원칙" (캐릭터 아이덴티티 유지 범위, 발바닥 기준선, 몸통 중심 고정, 밉맵)
- §3 표 (비숑 기준 상태별 프레임/FPS/loop — 새 캐릭터도 같은 상태 세트를 기본으로 삼음)
- §4.3 "런타임 등록 계약" (다음 단계인 `gd-integrator`에게 넘길 실측값 형식)
- §8 "인수인계 템플릿"

## 절차 — 모든 캐릭터가 동일: 10개 상태 전부를 애니메이션 시트로

**(2026-08-06 갱신) "정지 이미지만 만드는 포즈 등급"은 폐지됐다.** `char-designer`가 스펙 최상단에 스코프 축소를 명시하지 않았다면, 항상 아래 10개 상태 전부를 여러 프레임짜리 애니메이션 시트로 만든다 — 정지 이미지 1장짜리 "포즈"는 더 이상 허용되지 않는다.

`Idle` / `Walk`(구 walk1+walk2 통합) / `Sleep` / `Eat` / `Sick` / `Sulk` / `Happy`(=Pet 반응) / `Dragged`(잡힘) / `Fall`(떨어짐) / `Land`(착지)

1. **필독**: `docs/02-design/pet-sprite-production-guide.md` 전체, 특히 §2(시각 원칙)·§3(상태별 프레임 계약 — 지금은 bichon 전용 문서지만 프레임/FPS/loop 계약 자체는 모든 캐릭터에 동일 적용)·§4.3(런타임 등록 계약)·§8(인수인계 템플릿). Dragged/Fall/Land는 bichon의 기존 값(`scenes/pet/pet.gd`의 `BICHON_ANIMATIONS["Dragged"/"Fall"/"Land"]`)을 참고해 같은 논리(잡혀서 흔들림 4프레임 / 낙하 4프레임 / 비반복 착지 4프레임)로 만든다.
2. **sprite-gen 실행**: `Skill(sprite-gen)`을 로드하고 `component-row` 엔진으로 캐릭터 기준 포즈부터 시작한다. 기존 산출물(`assets/generated/sprites/bichon-idle-blink-v2/`의 `sprite-request.json`)을 템플릿으로 참고해 `cell`, `chroma_key`, `states` 스펙을 구성한다.
3. **10개 상태 전부**: 위 10개를 sprite-gen의 생성→큐레이션→크로마키 정리→프레임 추출 파이프라인으로 전부 만든다. **하나라도 빠뜨리고 다음 단계로 넘기지 않는다.** 시간이 부족하면 10개 전부를 프레임 수를 줄여서라도(예: Walk를 4프레임으로) 채우는 게 몇 개만 정교하게 만들고 나머지를 비우는 것보다 낫다.
4. **시각 QA (제작자 자신의 1차 검수)**: 매 상태 완성 시 제작 가이드 §6 "정적 점검" 체크리스트를 스스로 확인한다.
5. **런타임 자산 배치**: 최종 PNG를 `assets/sprites/{character_id}/`에 상태별로 놓는다. 파일명은 `<state>_<frames>f_alpha_smooth.png` 또는 `<state>_<frames>f_chromakey_smooth.png`. sprite-gen 작업 기록(`assets/generated/sprites/{id}-v1/`)은 보존한다.
6. **실측값 정리**: 각 상태의 `columns`, `rows`, 논리 `frames` 수, `fps`/`loop`, idle 알파 바운딩박스 실측 높이, 프레임별 `foot_padding`/`horizontal_offsets`.
7. **인수인계 템플릿 작성**: 제작 가이드 §8 템플릿을 채워 `docs/02-design/characters/{character_id}.handoff.md`로 저장한다.

## 레거시 캐릭터 업그레이드 (정지 이미지 → 애니메이션)

기존 12종(mochi, ppiyak, haemjji, kkubeok, nyang, kong, mundeok, geobujang, bulgeumjo, seureureuk, tokki, ddungsil)은 `assets/sprites/chars/<id>/`에 정지 이미지 8장(idle/walk1/walk2/sleep/happy/sulk/sick/eat)만 있는 구세대 자산이다. 업그레이드 요청을 받으면:
1. 기존 8장을 아이덴티티 참고용으로만 쓴다(실루엣·색·표정) — 그대로 재사용하지 않는다, 정지 이미지 그 자체가 애니메이션이 아니므로.
2. 위 10개 상태 절차를 처음부터 그대로 수행해 애니메이션 시트를 새로 만든다. `walk1`/`walk2`가 통합된 `Walk`가 되고, `Dragged`/`Fall`/`Land`가 신규로 추가된다.
3. 기존 정지 이미지 8장은 삭제하지 않고 보존한다(`gd-integrator`가 등록 전환할 때까지의 폴백, 또는 회귀 비교용).
4. 진화 단계가 있는 캐릭터는 `_evolved`/`_evolved2`도 순서대로(base 먼저, 완료 확인 후 진화 단계) 같은 방식으로 진행한다 — 한 캐릭터를 세 단계 동시에 벌리지 않는다.

## 스코프를 의도적으로 줄여야 할 때 (테스트/프로토타입)

파이프라인 자체를 검증하는 목적 등으로 위 절차를 다 못 채우는 게 맞는 상황이라면, 결과물을 실제 캐릭터처럼 취급하지 않는다. 스펙 파일 최상단에 스코프 축소가 이미 표시돼 있어야 하고(없으면 되돌아가서 `char-designer`에게 표시를 요청한다), 완료 보고에도 "N/10 상태만 제작, 나머지는 미완성 — 실제 배포 전 완성 필요"를 명시한다. 이 표시가 없는 산출물은 `gd-integrator`가 10개 상태 완비로 간주하고 등록하므로, 표시를 빠뜨리면 미완성 캐릭터가 완성작으로 게임에 들어간다.

## 흔한 실수 (제작 가이드에서 반복 강조되는 것들)

- 포즈마다 캔버스 안에서 캐릭터 위치가 달라 몸통이 흔들리는 것 — sprite-gen 생성 시 기준 앵커를 프롬프트에 명시해도 어긋날 수 있으니 프레임 추출 후 반드시 비교한다.
- 부화 전/후 두 성장 단계(baby/adult)에서 같은 스케일 배수를 그냥 복사하는 것 — 캐릭터마다 원본 아트가 캔버스를 차지하는 비율이 다르므로 실측이 필요하다.
- 큰 원본을 축소 표시하면서 밉맵을 안 켜는 것 — `.import` 파일에 `mipmaps/generate=true`가 있는지 반드시 확인한다 (없으면 `gd-integrator`에게 `.import` 설정 보완을 요청한다).

## 실측 규칙 — 코어 몸통은 최대 연결성분으로 재고 이펙트를 제외한다 (2026-08-11 추가)

`characters.gd`의 `BODY_CORE_HEIGHT`는 "코어 몸통 높이(px @캔버스, `idle.png`, α>0.125)"이고
판정 규칙에서 **이펙트(Zzz·반짝임·김·불꽃)와 소품(모자·가방)을 제외**한다. 실측할 때는
**알파 마스크의 최대 연결성분만** 재야 한다.

⚠️ **naive 알파 bbox로 재면 틀린 결론이 난다.** 실측 사례(mochi base):

| 포즈 | naive bbox | 최대 연결성분 | 차이 |
|---|---|---|---|
| `sleep` | 87px | **69px** | Zzz 이펙트 18px |
| `happy` | 80px | 77px | 반짝임 3px |
| `sick` | 70px | 67px | 반짝임 3px |
| `idle`·`sulk`·`walk2` | 72px | 72px | 이펙트 없음 |

`sleep`을 87px로 잘못 재면 "1.5배 확대 시 130px이라 128 캔버스 초과 → 작업 불가"라는
**틀린 결론**이 나온다. 실제로는 69px이라 확대해도 들어간다. 이번에 그 판단 직전까지 갔다.

## 눈 크기 실측 — 어두운 덩어리 3조건 (mochi·mundeok·tokki 예외 종족용)

몸통 정규화 예외 3종은 `BODY_SCALE`이 몸통이 아니라 **눈 크기**(mochi) 등 별도 기준으로
잡혀 있다. 눈을 실측할 때는 어두운 연결성분 중 아래 **세 조건을 모두** 만족하는 쌍을 잡는다:

1. 채움률 ≥ 0.45
2. 종횡비 0.6 ~ 1.6
3. 높이 차 15% 이내의 **좌우 쌍**

세 조건이 다 필요하다. 실측된 오검출 사례:

- **(1)·(2)가 없으면** 눈·입·볼이 한 덩어리로 뭉쳐 40px로 나온다(실제 16.5px).
- **(3)이 없으면** `mochi_evolved2`의 금테 안경을 눈으로 잡아 48px, 양복을 잡아 오검출한다
  (실제 32px).
- 외곽선도 눈과 같은 어두운 색이므로 **실루엣에서 3px 안쪽으로 침식(erode)한 영역만** 본다.
- **눈 감은 포즈(`sulk` 등)는 검출 불가**다 — 눈 기준 검증은 눈 뜬 포즈로 한다.

검증된 구현: `probe_tier_size.gd`(GDScript) / `scratchpad/recompose/eyelib.py`(Python).
두 독립 구현이 같은 값을 낸다: base 16.5 / evolved 33.5 / evolved2 32.0.

## 알파 임계값을 도구마다 통일한다

측정과 크롭이 다른 임계값을 쓰면 배치가 어긋난다. **`PIL.Image.getbbox()`는 `alpha>0`**이라
반투명 프린지까지 포함해 bbox가 **최대 6px 커진다**. 측정은 `alpha>32`(또는 α>0.125)로
하면서 크롭만 `getbbox()`로 하면 그 차이만큼 프레임이 밀린다 — ppiyak Fall 재배치에서
실제로 발생해 단정문에 걸렸다. **한 스크립트 안에서 임계값을 하나로 통일할 것.**

## 몸통 크기를 바꾸는 작업은 "확대"로 되지 않는다

캐릭터의 눈/몸통 비율을 바꾸라는 요구(예: "눈은 유지하고 몸만 1.5배")는 **이미지 확대로
구현할 수 없다.** 몸통을 확대하면 몸통에 그려진 얼굴도 같이 커지고, 그 위에 원본 크기
얼굴을 얹어도 아래의 커진 얼굴이 남아 겹쳐 보인다. 지우고 인페인팅해야 하는데 결정론적이지
않다(2026-08-11 실측 시도·폐기). **비율 변경은 재생성만이 유효한 경로다.**

재생성 시 프롬프트는 절대 픽셀이 아니라 **비율**로 지정한다. 다만 **표현 방식에 따라 결과가
크게 갈린다.** mochi base 눈/코어 비를 0.229 → 0.153 으로 바꾸려 한 4회 실측(2026-08-11):

| # | 프롬프트 표현 | 참조 이미지 | 요청 | 실측 눈/코어 |
|---|---|---|---|---|
| v1 | `ONE SEVENTH` | 원본 | 0.143 | 0.1407 |
| v2 | `SIX AND A HALF TIMES` + 폭 제약 | 원본 | 0.154 | 0.1081 |
| v3 | `ONE SIXTH AND A HALF` | 원본 | 0.154 | 0.1088 |
| v4 | `15 PERCENT` | 원본 | 0.150 | 0.1377 |
| v5 | `17 PERCENT` (보정 시도) | 원본 | 0.170 | **0.0907** |
| v6 | **"눈만 10% 더 크게, 나머지는 동일"** | **v1 산출물** | +10% | **0.1516** |

### 절대 목표 지정은 통하지 않는다 — 델타 편집을 쓴다

v1~v5는 **원본을 참조로 절대 비율을 지정**했고 결과가 0.09~0.14 로 흩어졌다. **단조 관계가
없다** — 0.150 을 요청해 0.1377, 0.170 을 요청해 0.0907 이 나왔다. 즉 "목표보다 크게 요청해
보정한다" 는 통하지 않는다(v5 가 그 가설을 반증했다).

**성공한 방법은 델타 편집이다.** 가장 가까운 산출물(v1)을 **참조 이미지로 붙이고** "눈만 약 10%
더 크게, 나머지는 전부 동일" 처럼 **작고 구체적인 변경 하나만** 요청하면 0.1516 이 나왔다.
목표 0.1531 대비 −1% 다. 절대 목표(±30% 산포) 대비 훨씬 정밀하다.

절차: ① 원본 참조로 대략적인 비율을 한 장 뽑는다 → ② 그 산출물을 참조로 붙여 부족한 만큼만
델타로 요청한다 → ③ 실측해서 남으면 한 번 더 델타.

부수 교훈: **모호한 분수 표현을 쓰지 마라.** `ONE SIXTH AND A HALF` 는 `1/6 + 1/2` 로도 읽혀
0.108 로 무너졌다. 폭 제약을 빼고 다시 뽑아도 같은 값이었으므로 원인은 표현의 모호함이고
지시 경합이 아니다. 단위분수나 백분율처럼 해석이 하나뿐인 형태만 쓴다.

### 결정론 보정 — 눈만 키우는 것은 되고, 몸통을 키우는 것은 안 된다

델타 편집 후에도 비율이 남으면 **눈만 세로로 미세 확대**해 정확히 맞출 수 있다. 어두운 눈
형상을 가로 폭 그대로 세로로만 키워 같은 중심에 덮어 얹으면 **새 눈이 옛 눈을 완전히 가리므로
지울 것도 메울 것도 없다**. 반대로 **몸통 확대는 불가능하다** — 위에 적은 이유(얼굴이 같이
커지고 인페인팅이 필요)다. 구현: `scratchpad/recompose/scale_eyes.py`.

⚠️ **비율이 왜 타협 대상이 아닌가**: 몸통 정규화 예외 종족은 화면 눈 크기와 화면 몸통 크기가
각각 별도 요구조건으로 고정돼 있고, `눈/코어 = 화면눈 / (STAGE_SCALE x 화면몸통)` 이므로
**비율은 `BODY_SCALE` 과 무관하게 두 요구조건이 강제하는 유일한 자유도**다. "달성한 값을 그대로
등록하면 된다" 가 통하지 않는 유일한 항목이니, 어긋난 채로 넘기면 진화 크기 사다리가 뒤집힌다
(mochi 실측: 비율 0.109 면 base 몸통이 evolved 보다 커진다).

## 셀 수용 판정은 **행의 최대 프레임**으로 한다 (중앙값 금지)

시트를 확대·재배치할 때 "셀에 들어가는가"는 **가장 큰 프레임 하나**가 결정한다. 중앙값이나
f0 으로 판정하면 통과처럼 보이고 실제로는 넘친다.

실측 사례(2026-08-12, `haemjji_evolved/idle_6f`):

```
프레임      120x173  117x171  119x184  117x171  118x172  117x171
중앙값 172 기준 -> x1.10 이 들어간다고 오판       (172 x 1.10 = 189 <= 190)
최대값 184 기준 -> x1.10 은 202 로 셀 초과       (허용치 190)
실제 최대 균일 배율 = 190 / 184 = 1.0326
```

이 오판으로 `sheet_scale` 재계산 값까지 잘못 전달했다가 적용 직전에 되돌렸다. 단정문이
저장 전에 잡아 자산 손상은 없었다 — **배치 스크립트에는 셀 수용 단정문을 반드시 넣을 것.**

같은 축의 반대 방향 오판이 Zzz 함정이다(naive bbox 가 이펙트를 포함해 **과대**평가).
**둘 다 "행 전체를 하나의 수로 요약할 때" 생긴다** — 수용 판정은 최대, 이펙트 제외는
연결성분, 크기 기준은 f0 처럼 목적마다 다른 대표값을 쓴다는 것을 매번 확인해야 한다.

### 수치를 넘길 때 어느 통계량인지 함께 적는다

`120x172` 처럼 숫자만 넘기면 받는 쪽이 f0 인지 중앙값인지 최대값인지 알 수 없어 검산을 못 한다.
실제로 이 누락 때문에 잘못된 배율(x1.10)이 코드 반영 직전까지 갔다 — 받는 쪽이 "그 172 가
최대값이냐"고 되물을 수 있었다면 그 자리에서 잡혔을 것이다. 다음처럼 적는다:

```
idle f0 120x173 / 최대높이 프레임 f2 119x184 / 폭 중앙값 118
```

목적별로 필요한 통계량이 다르다: **셀 수용 = 최대**, **`sheet_scale` 분모 = f0**,
**티어 간 비교 = 중앙값**.

## 종횡비 문제를 배율로 풀려고 하지 마라

"폭이 좁다"는 결함은 **확대로 안 풀린다** — 폭을 맞추면 높이가 같이 커져 셀을 넘고, 셀에
맞추면 폭이 부족한 채로 남는다. 위 사례에서 최대 배율 1.0326 을 다 써도 진입 체인 팝이
18.8% → 15.1% 로 한도(15%)를 여전히 넘었다.

**필요한 것은 "더 크게"가 아니라 "같은 높이에 더 넓게"** — 종횡비 변경이고 재생성 대상이다.
부수 이점이 있다: 높이가 안 변하면 `sheet_scale`(분모가 Idle f0 높이)이 불변이라 코드 쪽
갱신이 없다.

## 이상치 판정은 형제 상태 전부와 대조한다

"A 상태가 B 상태와 어긋난다"에서 **어느 쪽이 이상치인지는 둘만 봐서는 알 수 없다.** 그 티어의
같은 성격 상태(휴식에서 시작하는 반응들) 전부와 대조해야 한다.

실측 사례: `haemjji_evolved` 의 Idle 이 FileHover 와 18.8% 어긋났을 때, Idle 을 8개 반응
상태(hover/consume/pet/poop/sick/sulk/eat/land) f0 폭 전부와 비교하니 **Idle 만 −10.1% 로
예외 없이 좁았다**. 반대로 `haemjji_evolved2` 는 −0.8% 로 정합해서, 같은 검사에서 13.7% 가
나왔지만 **아트 결함이 아니라 비교 프레임 선택의 문제**였다(손대면 오히려 어긋난다).

## 레터박싱 — 생성물이 크로마 띠 위아래에 흰 여백을 붙일 수 있다

행 이미지를 생성하면 크로마 배경 띠의 **위아래에 흰 여백이 붙어 나오는 경우**가 있다. 그대로
크로마 키잉하면 흰 띠가 지워지지 않고 **거대 연결성분**으로 남아 프레임 분리가 실패한다.

실측(2026-08-12, `haemjji_evolved/idle` 2차 델타): 6개를 기대했는데 8개가 검출됐고 상위 두
덩어리가 각각 351,864px(흰 띠)였다. 크로마 엔진도 배경을 `(253,253,253)` 으로 오검출한 뒤
선언된 키로 재매트했다고 경고를 남겼다 — **그 경고가 레터박싱의 신호다.**

대응: 키잉 **전에** 크로마 색이 과반인 행·열만 남기도록 크롭한다.

```python
isgreen = (rgb[...,1] > 150) & (rgb[...,0] < 130) & (rgb[...,2] < 130)
rows = np.nonzero(isgreen.mean(axis=1) > 0.5)[0]
cols = np.nonzero(isgreen.mean(axis=0) > 0.5)[0]
src = src.crop((cols[0], rows[0], cols[-1]+1, rows[-1]+1))
```

## 델타는 쌓을 수 있다 — 한 번에 안 되면 결과를 다시 참조로 넣는다

델타 편집도 요청량을 그대로 반영하지 않는다. 실측 2건 모두 **요청의 절반 정도**가 반영됐다:

| 대상 | 1차 요청 → 실현 | 2차 요청 → 실현 | 최종 |
|---|---|---|---|
| mochi idle 눈 비율 | (절대 지정 5회 실패) | 눈 +10% → 목표 대비 −1% | 통과 |
| haemjji_evolved idle 폭 | +12% → +5% | +8% → +8% | 18.8% → 5.3% |

**직전 결과를 다시 참조로 붙여 남은 만큼만 요청하면 수렴한다.** 한 번에 맞추려고 요청량을
부풀리지 마라 — mochi 에서 17% 를 요청했다가 0.0907(최악)이 나왔다.

## 같은 캐릭터의 여러 포즈를 다시 뽑을 때 — 참조 2장 델타

한 캐릭터의 정지 포즈 세트(8장)나 상태 시트를 새 비율로 다시 만들 때, 포즈마다 절대 지정으로
뽑으면 **8장이 서로 다른 비율로 흩어진다.** 대신 참조를 2장 붙인다:

```
ref1 = 이미 승인된 그 캐릭터의 새 기준 포즈(보통 idle)
         -> 몸 비율·눈 크기·색·외곽선·실루엣의 기준
ref2 = 기존의 그 포즈 아트
         -> 자세·표정·이펙트의 기준
프롬프트 = "1번의 몸으로, 2번의 자세를 그려라.
            2번의 비율은 따라하지 마라(그쪽 눈이 너무 크다)."
```

실측(2026-08-12, mochi base): `idle` 하나는 절대 비율 지정으로 **5회 실패**(0.09~0.14 산포)했는데,
나머지 **7포즈는 이 방식으로 7/7 첫 시도 성공**했다. 8장 간 정체성 일관성도 ref1 이 보장해서
따로 맞출 필요가 없었다.

### 포즈 간 크기 관계는 기존 배수로 보존한다

새 기준 포즈에 맞춰 배치할 때, 각 포즈의 코어를 **기존 아트에서 그 포즈가 idle 대비 갖던 배수**로
정한다. 예: 기존 `happy` 코어 77 = 기존 `idle` 72 × 1.069 → 신규 `happy` = 신규 `idle` 109 × 1.069
= 117. 이렇게 하면 스쿼시·스트레치 관계가 그대로 유지된다.

이펙트(Zzz·반짝임)는 최대 연결성분 밖이라 코어 측정에서 자동 제외되지만, **배치할 때는 몸통과
같은 배율로 함께 옮겨야** 원래 위치 관계가 유지된다.

### 접지는 배치 후 실측해서 1px 보정한다

배율·반올림 때문에 몸통 밑면이 목표 접지선에서 1px 어긋날 수 있다. 합성 후 실측해서 차이만큼
캔버스를 통째로 옮기면 된다. 포즈 간 1px 차이도 화면에서 상하 튐으로 보이므로 **세트 전체가
정확히 같은 접지값**이어야 한다.

### 표정에 따라 눈 높이가 달라지는 것은 결함이 아니다

같은 세트 안에서 눈 비율이 흩어져도(실측 0.088~0.170) 그것이 **표정 차이**면 정상이다 —
반쯤 감은 `sick` 은 보이는 눈 높이가 작고 활짝 뜬 `walk1` 은 크다. 눈 감은 포즈는 검출 자체가
안 된다. **`BODY_SCALE` 은 `idle` 하나만 쓰므로** 다른 포즈의 눈 비율은 코드에 영향이 없다.
눈 기준 검증은 항상 `idle` 로만 한다.
